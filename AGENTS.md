# Agent instructions

- Stack: Kotlin, Jetpack Compose, Compose Multiplatform for Web, Material 3, AGP, and Gradle Kotlin DSL.
- Work VS Code/CLI-first; the Gradle Wrapper is the build source of truth.
- Dependency versions are managed in `gradle/libs.versions.toml`; keep dependencies minimal.
- `:app` is the Android application host: it owns ViewModels, Navigation 3, DataStore, Room persistence, economy, ads, haptics, and Android platform adapters; it may depend on `:puzzle-core` and `:shared-ui`.
- `:platform-contracts` owns the small platform-neutral Store, Ads, Player Identity, Cloud Save, lifecycle, metadata/capabilities, and `PlatformServices` contracts in `commonMain`; it depends only on multiplatform primitives such as coroutines `StateFlow`.
- `:shared-ui` owns platform-neutral Compose Multiplatform presentation shared by Android and Web, including all seven gameplay presentations, the Game Catalog, and the gameplay Profile presentation/model; it never owns ViewModels, persistence, economy, ads, haptics, navigation, or platform SDK integrations.
- All seven games use shared Compose Multiplatform gameplay presentation with state-down/events-up host adapters, and their Catalog artwork is canonical Compose Multiplatform resources with compile-time mappings; future games extend this approach instead of adding platform-specific UI copies.
- Shared square-board gameplay follows one constraint-driven screen: metadata and tools stay visible, the header, board, and controls form one centred group, and the board adapts to both available dimensions without gameplay scrolling. In landscape the square board and a side panel (the same header over the large controls) form one centred row; Word keeps its board over the full keyboard in a centred column unless the window is too low, and the Game Hub lays its catalog cards out in two or three columns on wide screens.
- Catalog cards show their artwork without a scrim: the always-light artwork carries fixed dark ink with a soft glow and a light Play chip in both themes.
- Android gameplay hosts retain ViewModels, economy, persistence, haptics, Back guards, terminal/interstitial policy, navigation, and ads; shared presentation owns none of them.
- `:web-app` owns browser I/O, Yandex SDK bootstrap behind one bridge, Web lifecycle adaptation, lazy assets (fetched relative to the page, never the site root, because Yandex serves the game from a nested folder), the responsive host (a phone column in portrait or narrow windows that keeps the window's full width up to 4:5 of its height, so a sticky banner shortening the window never narrows it and wraps text; in a landscape window of 720 dp and more it fills the width up to 1440 dp with a navigation rail, a game grid, 2x2 difficulty cards, readable-width Profile/Store, tutorials with the instruction beside the example, and the games' side-panel layouts), and separate Web-only Catalog, statistics, and Daily persistence domains. Its lightweight game controllers launch Catalog levels (every Daily game also its Daily entry) from one attempt-source abstraction; Word and Sudoku load only the lexicon or Dataset V1 bucket required by that definition. SDK startup never hangs: a `YaGames.init()` without an answer within ~15 s shows a retry screen (a page reload), a `player()` without one within ~10 s binds through the ordinary unavailable path and its retry, and a failing `LoadingAPI.ready()` is not fatal.
- Android and Web remain separate entry points over the shared core, canonical data, and focused shared presentation.
- Android and Web implement the same neutral contracts from `:platform-contracts`; Android-specific adapters remain in `:app` under `platform/android/`, while Yandex/browser implementations remain in `:web-app`.
- Web implements the neutral `PlayerIdentityGateway` and `CloudSaveGateway`; one `YandexGamesBridge` instance is the only raw Yandex SDK boundary and is shared by bootstrap, Player identity, and the legacy separately keyed Catalog/statistics/Daily cloud keys, which remain readable only as a migration compatibility path. Web automatically uses the current Player supplied by the SDK, with no in-game authorization UX; `PlayerAuthorizationState` is identity metadata, not a Cloud Save permission gate.
- Web Catalog progress is one versioned snapshot per local namespace: each Yandex Player unique ID has an isolated browser-local scope, and standalone development has a separate scope. Local/cloud merge is allowed only within the same Player scope, keys buckets by `PuzzleType + Difficulty + CatalogLevelPackVersion`, advances monotonically by maximum current level, and never contains active gameplay sessions.
- Web statistics are a separate versioned local/cloud domain scoped to the exact Yandex Player or standalone namespace. Each fresh gameplay engine start receives a transient exactly-once statistics identity bound to that Player-context token; only true terminal attempts update the current installation's monotonic component, while voluntary unfinished exits record nothing. Local durability precedes serialized best-effort cloud synchronization, and statistics failure never blocks Catalog completion, Retry, or Next Level.
- Web statistics synchronization keeps same-device per-counter maximum merge, different-device component union, and Player aggregates derived by summing components (plus the archive). An installation's component appears only with its first terminal attempt, and beyond 12 components the ones with the fewest plays fold into a schema-2 archive — summed counters plus folded ids that every merge drops, archives merging by per-counter maximum, an installation whose own id was folded moving to a fresh id — so the section stays under ~40 KB. 2048 records SOLVED at its first V2 target crossing and never records again at the later freeplay game over. Web Profile consumes the currently bound Player aggregate reactively without exposing installation components or initiating a cloud read.
- The Daily Hub presentation is shared between Android and Web in `:shared-ui`: neutral hub models plus one compact section rendered through the shared Game Hub header slot. Android still owns `TodayViewModel`, Room Daily lifecycle, refresh, run creation, and its host Share action; the shared section receives an already formatted date label and never formats dates itself.
- Web Daily history remains a versioned Player-scoped local/cloud snapshot with standalone isolated: calendar date, immutable policy identity, monotonic failed/solved masks, and optional solved Word attempts; merge is idempotent, and on a same-date policy conflict it keeps the local record of that date while every other date still merges. Definitions stay deterministic in `:puzzle-core`, active attempts are never persisted, and Android Daily Room/UI stays platform-owned.
- Web Daily gameplay runs on the Player-scoped Daily repository through one token-bound `WebDailyGameplayCoordinator`: starts are local-first (`ensureRun` must land durably before gameplay), cloud sync is best-effort afterwards, attempts are transient token-bound identities, stale Player contexts are safe no-ops, and account switches invalidate them.
- Web error states carry a reason (`WebLoadFailure`: data load, data corrupt, progress unavailable, unknown; a failed fetch throws `WebPuzzleDataLoadException`), never an exception's text, and the level error screen, save-error lines, and the fatal startup screen show localized `WebRes` text in all three languages.
- Web pre-playing Loading/Error state carries a small Catalog/Daily launch identity, so Daily Back and Retry always stay Daily: they repeat the same attempt or return to the Game Hub and never fall into the Catalog difficulty flow.
- Web Daily terminal UI is driven by one shared per-controller completion persistence state: only an actually recorded local-durable mutation may claim the result saved; save retry repeats exactly that original Daily mutation (with its Word attempts) and never Statistics; cloud failure stays best-effort and never becomes SaveError. A successfully solved Daily entry, including Daily 2048, is not replayable from the terminal screen, while FAILED entries remain fresh real retries.
- Web Profile now consumes real Daily history metrics through the existing optional shared Profile Daily capability: completed count, current/best streak, the recent days, and the current month's calendar, derived locally from the bound Player's durable Daily repository without any cloud read on open.
- Completed Daily count remains full-completion based while current/best streak follow policy qualification rules (V5: any solved entry qualifies its date).
- Daily sharing uses one shared platform-neutral spoiler-free payload/formatter with platform-host share actions: Android keeps Intent-based sharing, Web shares user-initiated through the browser Web Share API with a clipboard fallback.
- Sharing is presentation-only and never changes Daily persistence, Statistics, or Catalog state; the Web Daily block is functionally complete after this stage.
- The Web economy foundation exists in `:platform-contracts` (EconomyState/events/policy) plus a Player-scoped `WebPlayerEconomyRepository` bound per Player context like Catalog/Statistics/Daily; wallet mutations flow through one processor and persist locally before publication, and reach the cloud through the unified save.
- The economy is the same on both platforms. Catalog and Daily terminals feed it through one gameplay seam (`WebGameplayEconomy.recordTerminalResult` on Web): a solved attempt pays the shared `PuzzleGemReward` table, a failed one costs one life, and confirming the exit from an unfinished attempt with real progress costs one life too (`recordAbandonedAttempt`). Web lives regenerate like Android (one per `EconomyPolicy.LIFE_RESTORE_INTERVAL_MS`, 30 minutes, from a stored anchor that another loss never restarts), and 0 lives blocks starting, retrying, or advancing a Catalog level or a Daily entry. Web lives, rewards, and the Daily date read one `WebClock`: once the SDK is ready every reading asks `ysdk.serverTime()` (the server time at page load plus the monotonic `performance.now()`, so moving the device clock while the page is open changes nothing); a failed or non-numeric reading uses the device clock shifted by the last good offset (zero before any), standalone uses the device clock, days follow the browser time zone, and the login gift and quest day only move forward.
- The shared Profile is compact: one summary card (solved, current streak with the best under it, Daily count, then gems, lives, and hints on one line) followed by one row per page, each opening its own page (`ProfilePage`, drawn by `ProfilePageContent`; Android `AppDestination.ProfileSection`, Web a page in place of the Profile with a way back, like the achievements): the Daily calendar, the game statistics, the achievements, and on Web the rating (the `solved` leaderboard), each with its own picture (`drawable/profile_<name>.webp`, cut from the transparent `art/profile/sheet.png`). The Daily page is a calendar of the current month (Monday first; a full Daily fills its date, a partly solved one is ringed, today carries a dot, each with a text description; hosts build the `DailyCalendarMonth` from durable history — Android from completed runs plus solved Daily results, Web from its Daily snapshot — and without one the recent days row remains), and the games page is one list of games where a played game opens to its details (played/failed/success rate, per-difficulty counts, Word attempt bars) and an unplayed one stays a single quiet line; the empty state offers a way to the games.
- Achievements (`Achievement` in `:shared-ui`, 22 goals over solved counts, stars, expert solves, Word first tries, full Dailies, and streaks) are derived from `ProfileStatistics` alone — nothing is stored for them, so they match wherever the statistics reach. The Expert achievements count Expert solves of every game except Word, whose statistics have no per-difficulty breakdown. The Profile shows one entry card (the count and a bar) that opens their own screen — Android `AppDestination.Achievements`, Web a page in place of the Profile with a way back — where the shared `AchievementsScreenContent` lists every achievement on its own row, reached ones first, the rest nearest first with their progress. Each reached achievement pays a one-time gem reward (`Achievement.gems`: 2/5/10/20 by how hard it is) that the player claims on its row, the Profile card counting the rewards waiting; players who reached achievements before rewards existed claim them once too. Android pays through `economy_events` rows `achievement:<id>`; Web keeps the paid ids in the Player-scoped daily rewards record (`LGDR2`, merged by union) and makes a claim durable before paying. Each achievement has its own picture (`Achievement.artwork`, `drawable/achievement_<name>.webp`, 192 px with transparency; one not reached yet is drawn grey and faded), cut by `tools/art/cut_sheets.py` from the generated sheets in `art/achievements/` — rerun it after replacing a sheet rather than editing the drawables. Hosts remember only which ids were already announced (Android DataStore `seen_achievements`, Web browser-local `logica_achievements_seen_v1:<scope>`; the first look records what is already reached, so nothing old is announced) and push new ones to the shared `AchievementAnnouncer`: an open result card claims them and shows them inside itself, otherwise `AchievementAnnouncementHost` shows a short banner.
- Both Stores use the shared `StoreBalanceCard`, `StoreItemRow`, and `GemPriceButton`: one balance card (gems, lives, hints, and on Web the next-life countdown), then compact item rows whose button is the price itself — RuStore's price label for Android gem packs, the Yandex catalog price on Web, a gem icon and cost for hints and lives — and a purchase the balance cannot cover says what is missing. Every row, the starter pack, and «no ads» show a shared `StoreArtwork` picture (a handful, pouch, or chest of gems by pack size, one hint or a pack, a life, rewarded gem/life with a play badge), cut by `tools/art/cut_sheets.py` from the transparent `art/store/sheet.png`; price buttons stay vector. Android top bars share the screen background. Wherever a currency is shown as an amount — the wallet chips (Android `StatusChip` with `artwork`, Web `WalletChip`), the Store balance card and starter pack tiles, the Profile summary, the result card's gem/life/hint tiles, and the gem rewards of quests and achievements — it uses the shared coloured `GameIcon` pictures (gem, heart, a broken heart at zero lives, hint; cut at 128 px from `art/icons/sheet.png`; every generated picture is drawn from its bitmap with `ArtworkFilterQuality`, mipmapped, since it is always shown well below its source size); buttons, game tools, and tabs keep tinted vector icons. The Web leaderboard shows places 1–3 as `RankMedal` (a gold, silver, or bronze medal with no number on it; numbers start at place 4).
- The Store foundation exists on Web: platform-neutral store contracts in `:platform-contracts`, plus a Player-scoped `WebPlayerStoreRepository` (inventory + bounded purchase history) bound per Player like Economy. Purchases use internal gems only through one `WebStoreProcessor` over the static `WebStoreCatalog` — the economy repository stays the single source of truth for gems.
- Hints are a consumable inventory item on both platforms: Sudoku, Balance, and Crowns spend one hint per shown hint from one shared stock, in Catalog and Daily alike; a new player starts with `STARTING_HINTS` (3), hints are restocked singly or in packs for gems (prices are provisional), and an empty stock never applies a hint but offers to restock. Web keeps the stock in the Player-scoped Store inventory (`tryConsumeHint`); Android keeps it in the wallet. A hint is computed first, then charged and shown only if the board is still the one it was computed for: Android does both in one non-cancellable step (`GameplayHints.chargeAndShow`) and ignores board input meanwhile, while on Web the check, the synchronous `tryConsumeHint`, and the update run with no suspension point between them.
- The Store screen is a primary-tab surface on Web with balance, catalog, purchase buttons, and result feedback; internal gem purchases, Yandex paid gem packs, rewarded +1 gem, and (while a life is missing) rewarded +1 life all run through it, and its inventory syncs through the unified save together with Economy. The Web no-lives dialog offers the same rewarded +1 life; each rewarded placement is its own `WebRewardedPlacementController` over one shared `AdKind.REWARDED` cooldown, and the life goes through the ordinary durable `restoreLives` wallet mutation.
- The monetization providers are wired into real Web/Yandex product flows over `:platform-contracts/Monetization.kt` and `web-app/WebMonetization.kt` (provider interfaces, `WebAdPolicy`, internal analytics, `WebRewardService`). The bridge passes `{ callbacks: { … } }` to `showFullscreenAdv`/`showRewardedVideo` — bare callbacks are ignored by the SDK, which would leave the continuation, the reward, and the fullscreen-ad lifecycle flag hanging. Every rewarded/interstitial invocation carries a runtime-only session id, and BOTH layers enforce exactly-once completion: per-invocation provider latches (error-then-close / repeated terminals resolve once) plus controller-side session validation. Rewarded sessions capture the current Player context at start and re-validate it before granting, so an account switch can never pay the new Player for an old session; the +1 gem and +1 life flow through ordinary durable wallet mutations. An in-flight Catalog interstitial (`catalog_next_level_interstitial`) locks the Next Level transition: duplicate taps are ignored and the original continuation runs exactly once even when ads are denied, unavailable, or fail. Interstitials appear only on a player's tap that leaves a game: Next Level, and through `LocalWebTransitionAd` (`gameplay_transition_interstitial`) every other way out — the gameplay Back/confirmed leave, Retry, To difficulty, and To games — all sharing that controller and its cooldown; nothing else ever opens one. Interstitials keep a 90-second cooldown and never come within the first 2 minutes of a Web session (`WebAdPolicy.SESSION_GRACE_MS`). Ad cooldowns begin only after the platform reports actual exposure (never for unavailable/failed-to-start requests), stay application-session-only, and are never part of Cloud Save.
- Fullscreen advertisements participate in the effective Web lifecycle itself: `WebHostLifecycle` owns one fullscreen-suppression input (`setFullscreenAdActive`), so ACTIVE requires visibility + focus (a window focus event or any tap/key press in the page, since inside the Yandex iframe the canvas can take input without `document.hasFocus()`; blur clears it) + no Yandex pause + no fullscreen ad — GameplayAPI and audio consumers derive from that single state, and closing an ad recomputes instead of blindly resuming. Sticky banners stay platform-rendered behind `YandexGamesBridge`: the controller tracks desired vs applied visibility, suppresses transitions during fullscreen ads, and retries unapplied changes on later event-driven reconciliation (with optional platform-status healing).
- The unified cloud save foundation exists in `:platform-contracts/CloudSaveContracts.kt` (`SaveData`/`SaveRepository`/`CloudSaveProvider`) and `:platform-contracts/PlayerProvider.kt`. Web identity comes automatically from the Yandex SDK via `YandexPlayerProvider` — there is no custom authentication, login UI, or account creation anywhere. `web-app/WebCloudSaves.kt` keeps the versioned-save codec, the local fallback repository, per-domain section adapters over the bound Player repositories, and one `WebSaveManager`; it orchestrates sections only and never interprets business logic.
- Unified save is operational and is the canonical future Web/Yandex cloud representation: after each Player binds, `WebUnifiedSaveScheduler.restoreAndEstablish()` merges legacy per-domain cloud payloads plus unified cloud into local state using each domain's own merge semantics, then writes one canonical `logica_unified_save_v1` snapshot. Legacy Catalog/Statistics/Daily cloud keys remain readable as a migration compatibility path but stop receiving durable writes once the unified snapshot owns the context.
- All unified restores use domain-owned merge semantics instead of blind global overwrite: monotonic Catalog levels, unioned multi-device statistics, policy-safe Daily history, and a revision-compared whole-pair Economy/Store restore (`WebEconomyStoreCoupledRestore`) applied through one explicit coupled group that never depends on section ordering and never splits a purchase into an impossible wallet/inventory mixture.
- Web paid gem packs are the Android packs as Yandex client-side consumables (`gems_50`/`gems_150`/`gems_500` for 50/150/500 gems, `WebPaidProduct`): fulfillment is keyed by the opaque `purchaseToken` (exactly-once), journaled durably before any domain mutation, then flushed to the canonical unified save (retried ~2s/~8s if that fails, without holding the Store) and consumed whatever the flush did, so a token never pays twice (a purchase whose site data is cleared before any cloud write lands is the accepted loss), and reconciled after each Player's unified restore through exactly one `getPurchases()` pass per bind. Prices come only from `payments.getCatalog()`: the Store shows `priceValue` with the portal currency icon from `getPriceCurrencyImage('medium')`, or the catalog's own `price` text (which already names the currency) while the icon is unavailable. The bridge decodes `payments.getPurchases()` as the direct purchase array the SDK returns; malformed results are a failed query (retryable), never "no pending purchases", and unknown `productID` values are recorded but never granted or consumed.
- Two more paid products exist on both platforms: the one-time starter pack `starter_pack` (100 gems, 5 hints, and every missing life; `GemPack.STARTER_PACK` / `WebPaidProduct.STARTER_PACK`, contents in the shared `StarterPackContents`) shown as the shared `StarterPackCard` until it is bought once, and the permanent «no ads» `no_ads` shown as the shared `NoAdsRow`. «No ads» turns off every interstitial (Android `InterstitialAdController` neither preloads nor shows; Web `WebInterstitialContinuationController` continues at once) and the Web sticky banner, while rewarded ads stay the player's choice. Android keeps both as ledger rows (`STARTER_PACK_PURCHASE` with its deltas, `NO_ADS_PURCHASE` with none, keyed `rustore:<purchaseId>`), reads RuStore non-consumables whatever their acknowledgement so a reinstall restores «no ads» on the next Store open, and exposes ownership as `OwnedPurchases`. Web records both in the fulfilled-token ledger (ownership of «no ads», through the one `ownsPaidProduct` rule, is what the bind's last successful `getPurchases()` lists — plus purchases confirmed since — and only without such an answer a ledger token for that product): the starter pack's hints join its Economy change as one journaled Economy+Store pair (payment journal V2 carries the Store target), and «no ads» is never consumed, so every bind's `getPurchases()` sees it again without paying twice.
- The Yandex I18N boundary lives only in `YandexGamesBridge` (`platformLanguage()` reads `ysdk.environment.i18n.lang`); `WebBootstrapController` resolves it once during normal Yandex startup through `resolveWebAppLanguage` into `WebAppLanguage` RUSSIAN/ENGLISH/TURKISH: ru, be, kk, uk, uz and a missing value mean Russian, tr means Turkish, anything else English. `applyWebAppLanguage` makes Compose resources follow it; standalone development never touches the SDK and reads `?lang=` or the browser language.
- The UI is localized into Russian (default), English, and Turkish: shared text in `:shared-ui` `values`/`values-en`/`values-tr`, Web-only text in `:web-app` `commonMain/composeResources` (`WebRes`), Android-only text in `app/src/main/res/values-en`/`values-tr`, whose `app_language` string (`AppLanguage`) picks the host's date and share formatting. Dates and the spoiler-free Daily share text are formatted per language; new user-visible text needs all three translations. A noun that follows a number goes through `<plurals>` and `pluralStringResource` in every module (Russian one/few/many/other, English one/other, Turkish one/other with the same text); Turkish speaks to the player with the informal «sen»; and in English «Leaderboard» is always a table of places while «Rating» is the player's own per-game points (Turkish «Sıralama» / «Puan»). Word is no longer part of new Daily runs (Policy V8). The Word game stays Russian-only in every language — its answers, guesses, and keyboard never change — and says so up front: it is titled «Russian Word»/«Rusça Kelime», its rules begin with that, and the difficulty screen shows the shared `WordLanguageNotice`.
- Economy/Store revisions are Player-context-scoped: every real durable mutation receives exactly one fresh revision from that context's timeline (no-ops allocate none), and external cloud/recovered snapshots are durable-first — they publish only after their local write succeeds, as one consistent Economy+Store pair (`WebEconomyStorePairApply`).
- Gem Store purchases are recoverable coupled transactions: the complete final Economy+Store pair is calculated up front, stamped with one shared transaction revision, journaled durably before either domain changes, applied atomically, then committed by clearing the journal; interrupted transactions finish idempotently during the next Player bind without double deduction, grants, or records, while failed purchases stay Store-only audit mutations.
- Unified cloud ownership becomes ACTIVE only after a canonical `logica_unified_save_v1` write actually succeeds; transient failures receive a small bounded retry (~2s/~8s) while legacy compatibility stays available until establishment, account switches invalidate pending saves and retries so no stale Player write can land, a cloud `getData` without an answer within ~10 s and a `setData` within ~15 s fail in `YandexCloudSaveGateway` (unified and legacy keys alike; the late answer is ignored), envelope size is validated against the Player data budget (an oversized envelope or section is a failed write with status ERROR, never an exception), and local repositories stay authoritative for gameplay durability whenever the cloud fails.
- The unified cloud is written (establish, coalesced saves, retries, `flushNow`) only after a definite restore — `SaveLoadResult.Found` with every section decodable, or `Missing` — for the current Player context; a failed read, an undecodable envelope, or an unreadable/unknown section leaves the context unresolved (decodable sections still merge, legacy sync continues, restore retries ~2s/~8s/~30s and on the next durable change) and never overwrites the cloud. A cloud section whose merge does not land durably in local state leaves the context unresolved too, and a known section its domain does not export right now is carried forward byte for byte from the envelope last restored or written for that context.
- Daily never advances Catalog progression — no level change, Next Level, or completion writes; `WebCatalogCompletionController` stays Catalog-only.
- Daily terminal attempts are real gameplay: they record normal Web Statistics (played/solved/failed plus hints and Word attempts), while unfinished voluntary exits persist nothing anywhere.
- V5 first-solve streak qualification stays visibly separate from full 5/5 completion everywhere, including the shared hub presentation.
- Daily 2048 differs explicitly from Catalog 2048: a target crossing records nothing and play continues; only the real final game state — no move left, or «Finish» after the target — resolves exactly one Daily result and one Statistics result.
- Android keeps its richer Daily completion card and spoiler-free Share; Web offers the same spoiler-free share text through its browser share adapter.
- The shared Daily entry row also scrolls by mouse drag (touch keeps the row's own scrolling), so desktop Web players reach every entry.
- Daily metrics are an optional shared Profile capability: Android supplies completed-Daily and streak values from its existing Room statistics aggregation, while Web derives the same values from its durable Player-scoped Daily history.
- Web follows the device light/dark preference through `isSystemInDarkTheme()` unless the player picks a theme in the Web settings (the gear on every tab: theme and sound), and `index.html` paints the theme background for both schemes so the page never flashes another color before the first frame: an inline script reads the theme the player picked from `logica_settings_v1` (format unchanged) so it wins over the device scheme, and a CSS loader (the game's name and a moving bar, no images or web fonts) stays until Compose's first frame removes it (`removeStartupLoader`). The SDK keeps `<script src="/sdk.js">`, the path Yandex documents for archives uploaded through its console. Web settings live in one browser-local `logica_settings_v1` key that is never Player-scoped or synced.
- Game sounds are synthesized offline by `tools/sounds/generate_game_sounds.py` into shared `files/sounds/*.wav` (no third-party audio; regenerate instead of editing). Shared presentation only reports `GameSound` events through `LocalGameSounds` — derived from state increases, so retries and restores stay silent — and hosts play them: Android through one `SoundPool` honouring the Sound setting, Web through Web Audio that loads after the first tap into a game (a tap resumes the audio context inside the gesture, as mobile Safari requires, but only while sound is allowed), fetches the sounds relative to the page (`Res.getUri` breaks under Yandex's nested `index.html`), plays a sound requested before its file is decoded only if it is ready within ~300 ms, honours the Web setting, and stays silent and suspended while the effective lifecycle is not ACTIVE or Sound is off (`tools/web/check_sounds.mjs` checks all of it in Chromium). 2048 and Block Sudoku sound once per move however many tiles merge or lines clear, and the move that wins or loses sounds only its outcome.
- Web has eight Yandex Games leaderboards (created in the Yandex Games console, whose technical names allow only `[a-zA-Z0-9]`, hence camelCase): `solved` for the Profile and one rating table per game — `ratingBalance`, `ratingCrowns`, `ratingWord`, `ratingSudoku`, `ratingNonogram`, `ratingBlockSudoku`, and `best2048`. `WebLeaderboardController` submits the bound Player's values through `YandexGamesBridge` (`ysdk.leaderboards`) whenever one grows — best-effort, one call in flight, spaced for the rate limit, restarting for another Player — and reads a table only when a screen shows it: the Profile's rating page shows `solved`, each rating sheet its own table. A guest Player's submissions simply fail and they still see their points. Nothing about the tables is persisted or synced, and standalone development never shows them.
- Every game has a rating, shown from the difficulty screen («Рейтинг», next to «Как играть?») in the shared `GameRatingSheet`. `PuzzleRating` in `:puzzle-core` is the one rule: level games earn points per Catalog level cleared — Easy 1, Medium 2, Hard 3, Expert 4 — counted from progression as the current level minus one, so replays and the Daily add nothing and existing players are rated at once; 2048 is rated by its best single-game score (Catalog levels with their freeplay, and the Daily). The best score is the only new record: Android keeps it in the `records` DataStore (`Game2048BestScore`, conflated writes outside any screen), Web in the Player-scoped `logica_best_2048_v1:<scope>` key beside Catalog progress, recorded move by move and published (unified-save section `best2048`, merged by maximum) when a game ends or is left. Android shows the player's own points only; Web adds the game's Yandex table.
- The Nonogram difficulty screen also has «Галерея» (shared `NonogramGallerySheet`): every cleared level's picture per difficulty, newest first, with its best stars, and a tap enlarges one. Nothing is stored for it — levels are cleared in order, so the gallery lists 1..current-1 and each host rebuilds the pictures from the frozen level pack (`LevelStarRecord.level` carries the level number for the stars). A «Задача дня» chip lists every solved Daily picture with its date, rebuilt from the Daily entry's seed (Android from solved Daily Nonogram results, Web from its Daily history).
- Web primary navigation is Games, Profile, and Store; each tab opens with its title and the wallet (the Store too, above its full balance card), game sub-routes and tutorials hide primary navigation, and the difficulty screen and gameplay share one `WebTopBar` — the way back, a truly centred game title, and lives and gems that open the Store sheet.
- Web desktop keyboard input: one page-lifetime `WebKeyboard` document `keydown` listener forwards platform-neutral `GameKey`s from `:shared-ui` only while a puzzle is actively played with nothing over the board (dialogs call `PauseGameKeysWhileShown`), and only forwarded keys suppress the browser default. 2048 uses arrows; Sudoku uses arrows, 1–9, 0/Backspace/Delete, and the P key for Pencil; Word types Russian letters from the Russian layout or by ЙЦУКЕН key position, with Enter, Backspace/Delete, and Left/Right, inside the shared presentation. Balance and Crowns stay pointer-only.
- Web SOLVED completion advances local durable Catalog progress before normal navigation can reset the attempt, then requests asynchronous best-effort cloud synchronization; reset cannot cancel an earned local advancement, FAILED never advances, and Next Level always reloads the authoritative repository level.

- Block Sudoku (`PuzzleType.BLOCK_SUDOKU`, «Блок-судоку») is the seventh Catalog game and enters the Daily with Policy V7 (Web `WebBlockSudokuController.startDaily`, Web Daily bit 6 appended after the Nonogram; Android reuses its launch-generic ViewModel, and `TodayViewModel` lists every Daily game it may open). `BlockSudokuRules`/`BlockSudokuEngine` in `:puzzle-core` `blocksudoku/` are frozen Rules V1 (`GeneratorVersion(1)`): a 9x9 board, three pieces per deal from each difficulty's weighted shapes (deal k draws from its own stream derived from the level seed, so the pieces never depend on where earlier ones were placed), full rows, columns, and 3x3 boxes clear together, a placement scores its cells plus twice the cleared cells times the units cleared at once. A level is cleared at its target score — 300/600/900/1200 for EASY/MEDIUM/HARD/EXPERT — and fails when no tray piece fits; there are no mistakes, hints, stars, Undo, level map, or second chance. Its frozen V1 buckets use pack code 7 (Web codecs also 7); the gem reward is `PuzzleGemReward` like 2048, the rating counts cleared levels (Web table `ratingBlockSudoku`), Profile reuses 2048's statistics shape (`ProfileStatistics.blockSudoku`), and `BLOCK_SUDOKU` asks for 25 solves while `ALL_GAMES` still means the first six. Pieces are dragged from the tray (carried with their bottom edge 24 dp above the finger whatever their height, with a landing preview and the lines it would clear; `blockSudokuDropAnchor` snaps to the nearest fitting anchor at most half a cell beyond rounding, and the preview and the drop use that same anchor) or tapped and then placed with a tap on the board. The Catalog artwork `game_block_sudoku.webp` is a programmatic placeholder until real art replaces it.
