## 1. Одно скорректированное время на сервере Яндекса

### Как сейчас

Всё время на вебе берётся из `Date.now()` (`Main.kt:305`, `WebEconomy.kt:404`, `WebLives.kt`, дата Daily в `WebDailyRepository.kt`). Если перевести часы устройства:

- **Подарок за вход.** `WebCatalogProgress.kt:~351` отказывает только при `lastGiftEpochDay == today`, поэтому переключение часов между днём D и D+1 выдаёт подарок каждый раз.
- **Задания.** `WebDailyRewardsSnapshot.on()` (`WebDailyRewards.kt:~46`) сбрасывает полученные задания при любой смене дня, в том числе назад. После каждого переключения часов задания можно получить снова.
- **Жизни.** Перевод часов вперёд на 2,5 часа восполняет все жизни.

### Что сделать

1. **Одна функция «сейчас».** Ввести `WebClock` (или подобное) — единственный источник времени на вебе для экономики, наград и даты Daily.
   - Где брать смещение. На старте, после инициализации SDK, вычислить `offset = ysdk.serverTime() - Date.now()`. Вызов SDK — только в `YandexGamesBridge`.
   - Что возвращать. `now()` даёт `Date.now() + offset`.
   - Когда смещение равно 0. Это standalone, отсутствие `serverTime` или ошибка его вызова.
2. **Локальный календарный день** считается от скорректированного времени с часовым поясом браузера. Подмена часового пояса — принятый остаточный риск.
3. **Кто переходит на `WebClock`:**
   - восстановление жизней (`WebEconomy`, `WebLives`, обратный отсчёт в магазине);
   - день подарка за вход и заданий;
   - дата Daily (хаб, профиль, полуночный таймер).

   Кулдауны рекламы можно оставить на `Date.now()`: они живут только в сессии.
4. **День наград только растёт:**
   - подарок выдаётся, только если `today > lastGiftEpochDay`;
   - снимок наград сбрасывает задания только при `day > storedDay`;
   - при `day < storedDay` награды текущего дня недоступны и ничего не сбрасывается;
   - слияние наград (`mergedWith`, «более поздний день побеждает») не меняется.

## 2. Статистика: компонент только у играющих и ограниченный рост

### Как сейчас

- **Компонент создаётся при привязке.** `WebStatisticsRepository` (~строки 150-160) сразу добавляет компонент текущей установки, даже если игрок не сыграл ни одной партии. Каждое окно инкогнито и каждая очистка данных сайта навсегда добавляют компонент: при слиянии компоненты объединяются.
- **Лимиты не согласованы.** Секция статистики может дорасти до 120 КБ (`WebStatistics.kt:351`), а весь конверт ограничен 100 КБ (`WebCloudSaves.kt`).

### Что сделать

1. **Ленивое создание компонента.** Компонент текущей установки появляется в снимке только при первой записи терминальной попытки. До этого снимок, профиль и облако его не содержат. Существующие пустые компоненты в старых снимках убирать не нужно.
2. **Измерить реальный размер.** В отчёте приведи размер одного типичного компонента и сколько их помещается в бюджет.
3. **Сжатие при превышении.** Если компонентов больше `MAX_ACTIVE_COMPONENTS` (выбери число, при котором секция гарантированно занимает не больше ~40 КБ), компоненты сверх лимита сворачиваются в один архив.
   - **Какие компоненты сворачивать.** Самые маленькие по числу сыгранных партий. Компонент текущей установки не сворачивается никогда.
   - **Архив:**
     - суммы счётчиков;
     - множество id свёрнутых компонентов, его можно ограничить по размеру.
   - **Слияние со сжатием:**
     - множества свёрнутых id объединяются;
     - компоненты с id из этого множества отбрасываются;
     - два архива сливаются по максимуму каждого счётчика.

   Допустим небольшой недосчёт при одновременном сжатии на двух устройствах. Пересчёт недопустим: одна партия не должна учитываться дважды.

   Если тебе кажется, что сжатие в такой постановке хуже, чем без него, предложи вариант проще в отчёте, но п. 1 и п. 4 сделай в любом случае.
4. **Бюджет конверта.** Сумма лимитов секций не должна превышать бюджет конверта. Если секция статистики всё же слишком велика, `persist()` возвращает `false` и статус `ERROR`, а не бросает исключение. Проверь, что так и есть.

Логику архива держи в домене статистики (`WebStatistics*`), а не в `WebSaveManager`.

## 3. Старт SDK не зависает

### Как сейчас

- `YaGames.init()` и `player()` вызываются без таймаута (`YandexGamesBridge.kt:~88-116`), и приложение может навсегда остаться на экране загрузки.
- Исключение из `LoadingAPI.ready()` переводит всё приложение в `FatalError` (`WebBootstrapController.kt:~114`).

### Что сделать

- **Таймаут `YaGames.init()`** — около 15 с. После него показывается экран ошибки с кнопкой «Повторить», которая повторяет инициализацию. Если повтор внутри страницы невозможен, кнопка перезагружает страницу. Тексты — в `WebRes` на трёх языках.
- **Таймаут `player()`** — около 10 с. После него привязка идёт по существующему пути недоступности (`unavailable(...)` в `WebPlayerSessionController`), и существующий повтор продолжает работать.
- **Ошибка `LoadingAPI.ready()`** не фатальна: игра продолжает работать.

## 4. Daily: конфликт политики больше не стирает облачные даты

### Как сейчас

`WebDailyMerger.merge` при конфликте политики на одной дате бросает исключение на весь снимок, и `mergeCloud` возвращает `PolicyConflict`. Дальше `persist()` экспортирует локальный снимок, и облако теряет все даты, которых нет локально. Это нашёл исполнитель в отчёте 1a.

### Что сделать

- Слияние объединяет все даты.
- На дате с конфликтом политики остаётся локальная запись, облачная для этой даты отбрасывается.
- Результат — обычный `Merged`, с `cloudWriteRequired`, если облако отличается.
- `PolicyConflict` можно оставить как информацию (например, список дат), но потерю других дат он больше не означает.
- Так же исправь legacy-синхронизацию daily в `WebPlayerSessionController`, если она использует то же слияние.
