# Этап 2.1. Веб: одна активная вкладка, журналы без отката, платежи и «без рекламы»

Перед работой прочитай `AGENTS.md` и `tasksandreports/README.md`. Работа идёт прямо в `main`. Без попутных рефакторингов.

Этап 2 разбит на две задачи. Это первая: деньги и кошелёк. Вторая (2.2) — время, статистика, старт SDK.

## 1. Одна активная вкладка игры

### Как сейчас

Каждый репозиторий (`WebEconomy.kt:~529`, `WebStore.kt:~302`, `WebPayments.kt:~239`) держит копию данных в памяти и сохраняет её целиком. Синхронизации между вкладками нет: ни события `storage`, ни `BroadcastChannel`, ни `navigator.locks`.

Эксплойт без DevTools: во вкладке A купить подсказки за гемы, затем во вкладке B сделать любое изменение кошелька. Гемы вернутся, подсказки останутся. Тем же путём можно потерять оплаченную пачку гемов.

### Что сделать

1. **Захват блокировки.** На старте страница запрашивает Web Lock `navigator.locks.request("logica_active_tab", { ifAvailable: true }, …)` на одно имя для всего origin и держит его, пока вкладка активна.
   - Блокировку держит промис, который не разрешается, пока вкладка активна.
   - Весь JS-интероп — только в `:web-app`.
2. **Блокировка занята.** Вкладка не привязывает Player-контекст, не загружает и не пишет никакие репозитории и не запускает игру. Она показывает экран «Игра открыта в другой вкладке» с кнопкой «Играть здесь».
3. **«Играть здесь».** По `BroadcastChannel("logica_active_tab")` уходит запрос на передачу. Активная вкладка, получив его:
   - инвалидирует свой контекст так же, как при смене аккаунта (`invalidateContext`, отмена попыток, сброс транзиентного геймплея; незаконченная партия теряется без штрафа);
   - отпускает блокировку и сама показывает тот же экран.

   Новая вкладка ждёт блокировку (запрос уже без `ifAvailable`) и после захвата идёт обычным путём старта. Обрати внимание: таймер отложенной облачной записи старой вкладки отменяется до освобождения блокировки.
4. **Без `navigator.locks`.** Если API нет (старый браузер), работаем как сейчас, без защиты. Опиши это в отчёте.
5. **Standalone-разработка** использует тот же механизм.
6. **Тексты** экрана и кнопки — в `WebRes` на трёх языках (ru/en/tr).

Логику выбора и передачи вынеси в небольшой класс с интерфейсом над браузерными API (`WebTabLock` или подобный), чтобы её можно было протестировать фейком.

## 2. Журналы покупок не откатывают кошелёк

### Как сейчас

Журналы хранят абсолютные целевые снимки:

- покупка за гемы — `WebPurchaseTransactionRecovery.recover`, `WebStore.kt:~763`;
- платная выдача — `WebPaymentsCoordinator.recoverPendingFulfillment`, `WebPayments.kt:~742`.

Если применение не удалось (например, переполнен `localStorage`) или молча не удалось `journal.clear()` (`WebStore.kt:503`, `WebPayments.kt:721,762`), журнал остаётся. При следующей привязке Player он накатывает старый абсолютный снимок поверх всех изменений, сделанных после. В итоге откатываются потраченные гемы и потерянные жизни. Кроме того, интерфейс сказал игроку, что покупка за гемы не удалась, а потом она «завершается».

### Что сделать

Опирайся на ревизии.

1. **Проверь монотонность ревизий.** Ревизии контекста (`WebPlayerStateRevisions`) должны быть строго монотонны внутри Player-контекста, в том числе между перезагрузками страницы. Если это не так, исправь это и опиши в отчёте. На этом строится всё остальное.
2. **Покупка за гемы** (журнал транзакции с ревизией `R`). Пусть `cur` — максимум текущих ревизий economy и store.
   - `cur < R` — после журнала изменений не было. Применяем пару, как сейчас.
   - `cur == R` и текущая пара равна цели — покупка уже применена, только чистим журнал.
   - Иначе журнал устарел: после него были другие изменения, а игрок видел «покупка не удалась». Журнал удаляем, ничего не применяя.
3. **Платная выдача — деньги уже заплачены, её нельзя отбрасывать.**
   - Токен уже в журнале выдач (`payments.isFulfilled`) — только чистим журнал.
   - Нет, и `cur < R` — применяем как сейчас.
   - Нет, и журнал устарел — выдаём награду продукта заново как дельту к текущему состоянию с новой ревизией, тем же путём, что и `fulfillPurchase`: журнал, затем пара, затем ledger. После этого чистим старый журнал. Награда выдаётся ровно один раз за токен.
4. **Сбой `journal.clear()`** больше не опасен: правила выше распознают уже применённый или устаревший журнал. Повторная попытка очистки происходит при следующем восстановлении.
5. **Формат журнала** — локальный ключ, не облако. Его можно расширить, только если без этого не обойтись. Тогда старый формат должен читаться: старый журнал без новых полей обрабатывается по тем же правилам ревизий.

## 3. Платные расходуемые товары не выдаются повторно

### Как сейчас

`completeFulfillment` (`WebPayments.kt:~636`) потребляет токен только после успешного `flushNow()`. Если облачная запись не удалась, токен остаётся, а отметка о выдаче живёт только локально.

Эксплойт: заблокировать в DevTools запрос `setData`, купить, очистить `logica_payments_v1`, перезагрузить — гемы выдаются снова, и так сколько угодно раз. Тот же сценарий получается честно: сбой облака, потом другое устройство.

### Что сделать

После локально надёжной выдачи:

1. попытаться выполнить `flushNow()`;
2. если не удалось — повторить ограниченно (например, через ~2 с и ~8 с, без блокировки интерфейса);
3. после этого потребить токен в любом случае.

Это осознанный компромисс: повторной выдачи больше нет. Остаётся редкий риск — игрок купил при недоступном облаке и сразу очистил данные сайта, пока запись не дошла. Тогда покупка теряется. Такой риск принимаем.

Дополнительно:

- Постоянные товары (`no_ads`) по-прежнему никогда не потребляются.
- Состояние `CloudPending` в интерфейсе после этого больше не нужно для расходуемых товаров. Проверь, где оно показывается, и убери его, если оно стало недостижимым.
- Строку в `AGENTS.md` про «flushed to the canonical unified save before consumption» перепиши под новое правило.

## 4. «Без рекламы» — по живому `getPurchases()`, а не только по журналу выдач

### Как сейчас

Владение — это токен `no_ads` в журнале выдач (`Main.kt:136-141`, `WebStoreScreen.kt:209-211`). Подделанная запись в `localStorage` отключает всю рекламу и через объединение при слиянии навсегда уходит в облако.

### Что сделать

Владение вычисляется одной функцией, которой пользуются и `Main.kt`, и `WebStoreScreen.kt`:

- если в текущей привязке Player `getPurchases()` хотя бы раз успешно ответил, «без рекламы» есть, только если в его ответе есть покупка `no_ads`;
- пока успешного ответа в этой привязке не было (запрос упал, не поддерживается, standalone), действует прежнее правило — по журналу выдач;
- записи из журнала выдач не удаляются.

Результат последнего успешного `getPurchases()` храни только в памяти на привязку Player. При смене Player он сбрасывается.

## 5. Пределы значений и переполнения

1. **Декодирование.** Декодеры economy и store (локальные и облачные секции) больше не должны принимать значения, ломающие инварианты:
   - гемы — `0..MAX_GEMS`, где `MAX_GEMS = 1_000_000`, константа в `EconomyPolicy`;
   - жизни — `0..MAXIMUM_LIVES`.

   Значение вне диапазона приводится к границе. Снимок при этом не отбрасывается.
2. **Арифметика.** Сложение гемов насыщается на `MAX_GEMS`, во всех местах, где гемы прибавляются: награды, реклама, покупки, задания, достижения. Исключения из `require` в обработчиках нажатий больше не возникают.
3. **Подсказки, лимит 255** (`WebStore.kt:64`). Покупка подсказок, после которой станет больше 255, не начинается. Строка магазина показывает это так же, как нехватку гемов. Текст — на трёх языках.

## Тесты (webTest)

Покрыть:

- **Вкладки** (через фейковый `WebTabLock`):
  - вторая вкладка не привязывает контекст и ничего не пишет;
  - передача: старая вкладка инвалидирует контекст и больше не пишет, новая привязывается;
  - без `locks` поведение прежнее.
- **Журнал покупки за гемы**: три ветки — `cur < R`, уже применено, устарел. Устаревший журнал не откатывает жизни и гемы, потраченные после.
- **Журнал платной выдачи**: устаревший журнал выдаёт награду ровно один раз поверх текущего состояния. Повторное восстановление ничего не добавляет.
- **Платные расходуемые**: при неудачном `flushNow` после повторов токен потреблён, гемы выданы один раз. `no_ads` не потребляется.
- **«Без рекламы»**: подделанная запись в журнале выдач при успешном `getPurchases()` без `no_ads` не убирает рекламу. Настоящая покупка убирает. При упавшем `getPurchases()` действует журнал выдач.
- **Пределы**: декодирование с гемами `Int.MAX_VALUE` и отрицательными жизнями; насыщающее сложение; покупка подсказок около 255.

Каждую правку существующих тестов объясни в отчёте.
