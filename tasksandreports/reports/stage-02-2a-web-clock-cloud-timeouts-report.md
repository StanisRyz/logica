## 2. Что сделано по пунктам

### Пункт 1. `WebClock`: перевод часов при открытой странице

- **Источник времени — параметр.** Конструктор теперь `WebClock(deviceNowMs: () -> Long, serverNowMs: () -> Long? = { null })`. Бутстрап в `onReady` вызывает `clock.attachServerTime(bridge::serverTimeMs)` и больше не меряет смещение один раз. `synchronize(...)` удалён.
- **`now()` при каждом вызове читает `ysdk.serverTime()`** через `YandexGamesBridge.serverTimeMs()`. Это дешёвый синхронный вызов: SDK считает его локально, без сети.
  - Удачное чтение (положительное число) возвращается как есть и запоминает смещение `server - Date.now()`.
  - Исключение или не число: мост превращает и то и другое в `null`, а `WebClock` ещё раз ловит исключение источника. Тогда возвращается `Date.now() + lastOffset`.
  - Пока удачного чтения не было, смещение 0.
- **Standalone** серверный источник не подключает и остаётся на `Date.now()`.
- **Кто читает часы — без изменений.** Экономика, жизни, награды, дата Daily и таймер полуночи читают `webClock`, как и раньше. Кулдауны рекламы остаются на часах устройства: они живут только в сессии.

**Как SDK считает `serverTime()`.** Я разобрал загружаемый SDK `https://yandex.ru/games/sdk/v2`; публичная документация про это молчит. Реализация, если отбросить минификацию:

```js
this.serverTime = function () {
  const r = performance.timeOrigin || Date.now();                 // начало страницы
  const n = window.YandexGamesSDKEnvironment?.serverTime || r;    // серверное время от родительской страницы
  const a = window.YandexGamesSDKEnvironment?.parentTimeOrigin || r;
  const o = r - a;                                                // поправка на загрузку iframe
  return () => new Date(n + o + performance.now()).valueOf();
}();
```

Вывод: `serverTime()` **монотонный**. Это серверное время, которое площадка передаёт в окружение при загрузке, плюс `performance.now()`, а не `Date.now()`. Перевод часов устройства при открытой странице на него не влияет. Значит, после этого этапа такой перевод ничего не даёт: жизни не восполняются, дата Daily и день наград не сдвигаются. Своё монотонное время я не вводил.

Остаточные риски для решения отдельно:

1. **Нет `YandexGamesSDKEnvironment.serverTime`.** Если окружение его не передало, основой становится `performance.timeOrigin`, то есть часы устройства в момент загрузки. Тот же stub `serverTime: Date.now()` стоит в окружении SDK по умолчанию. Тогда перевод часов **перед** перезагрузкой страницы сдвигает время. На площадке Яндекса окружение заполняет родительская страница, поэтому это касается отладки вне площадки или сбоя окружения.
2. **Сон устройства.** В части браузеров и ОС `performance.now()` не идёт, пока устройство спит. Если страница была открыта во время сна, серверное время после пробуждения отстаёт от реального до перезагрузки. Это в ущерб игроку, а не в пользу: жизни восполняются позже, новый день наступает позже. Обойти это им нельзя.
3. **Резервный путь.** Пока `serverTime()` сбоит, время равно `Date.now() + lastOffset`, и в это окно перевод часов устройства снова действует. На практике сбой маловероятен: вызов локальный.
4. **Часовой пояс.** Подмена часового пояса по-прежнему двигает календарный день. Это принятый ранее риск, а день наград только растёт.

### Пункт 2. Таймауты облачных `getData`/`setData`

- **Таймауты стоят в шлюзе `YandexCloudSaveGateway`**, через `withTimeoutOrNull`:
  - чтение: `READ_TIMEOUT_MS = 10_000` → `CloudSaveReadResult.Failed`;
  - запись: `WRITE_TIMEOUT_MS = 15_000` → `CloudSaveWriteResult.Failed`.

  Через этот шлюз идут все пути: унифицированный ключ `logica_unified_save_v1` и legacy-ключи Catalog, статистики и Daily. Таймауты передаются в конструктор со значениями по умолчанию; `Main.kt` их не переопределяет.
- **Что дальше с `Failed`.** Неотвеченное чтение даёт `SaveLoadResult.Failed`, затем `UNRESOLVED` с повторами ~2/8/30 с по механике этапа 1. Неотвеченная запись даёт `persist() = false`, статус `ERROR` и ограниченный повтор ~2/8 с. `writeMutex` отпускается при выходе из `withLock`.
- **Поздний ответ игнорируется.** Таймаут отменяет ожидание промиса. Если промис потом выполнится, отменённое продолжение его отбросит.
- **Для теста шлюз зависит от узкого интерфейса.** Это `WebPlayerDataBridge` с `readPlayerData`/`writePlayerData`. Его реализует `YandexGamesBridge`; методы те же, добавлено только `override`.
- **Ожидание промиса стало отменяемым.** Общий `Promise.await()` в `WebPromiseAwait.kt` теперь использует `suspendCancellableCoroutine` вместо `suspendCoroutine`. Подробности — в разделе 5, п. 1.

### `AGENTS.md`

- Фраза о `WebClock` теперь описывает живое чтение `ysdk.serverTime()`: что SDK монотонный, резерв на последнее удачное смещение и standalone на часах устройства.
- В абзац об унифицированном облаке добавлено полпредложения о таймаутах `getData` ~10 с и `setData` ~15 с в `YandexCloudSaveGateway`.

## 3. Новые и изменённые тесты

Новый файл `WebCloudSaveTimeoutTest.kt` (webTest, виртуальное время `runTest`):

- `aHungReadFailsAfterTenSecondsAndItsLateAnswerIsIgnored` — legacy-ключ Daily:
  - на 9 999 мс чтение ещё ждёт, после 10 с — `Failed`;
  - поздний ответ промиса после этого ничего не меняет.
- `aHungWriteFailsAfterFifteenSeconds` — legacy-ключ статистики: на 14 999 мс запись ещё ждёт, после 15 с — `Failed`.
- `aHungUnifiedReadLeavesTheContextUnresolvedAndTheRetryRestores`:
  - зависшее чтение унифицированного ключа даёт `UNRESOLVED`, записей 0, владение не активировано;
  - повтор через ~2 с читает пустое облако и устанавливает каноническое сохранение.
- `aHungUnifiedWriteFailsReleasesTheWriteLockAndTheNextWritePasses`:
  - зависшая установочная запись через 15 с даёт `ERROR`;
  - сразу после этого `flushNow()` берёт `writeMutex`, запись проходит, статус `SYNCED`.

Изменённый `WebClockTest.kt`. Метода `synchronize(...)` больше нет, поэтому три теста переписаны под источник-функцию:

- **`theServerOffsetIsApplied` → `everyReadingAsksTheServerTime`.** Раньше тест проверял разовое смещение после `synchronize`. Теперь он проверяет то же смещение −3 ч при живом источнике: до подключения SDK — часы устройства, после — серверное время, и оно идёт вместе с источником.
- **`withoutAServerTimeTheOffsetIsZero`.** Смысл тот же, но вместо `synchronize(null)`/`synchronize(0)` источник возвращает `null` и `0`.
- **`aDeviceClockMovedForwardNeitherRestoresLivesNorOpensANewGift` → `aDeviceClockMovedForwardWhileThePageIsOpenNeitherRestoresLivesNorOpensANewGift`.**
  - Раньше часы устройства были впереди уже при старте; этот случай остался в первом тесте.
  - Теперь, по заданию, часы устройства сдвигаются на 3 ч **после** старта при неизменном серверном времени. Проверяется, что `now()` и дата не сдвинулись, жизни после `refresh()` не восстановились и второй подарок не выдан.
- **Новый `aFailedServerReadingKeepsTheLastGoodOffset`.** После исключения источника используется последнее удачное смещение; при ответе `null` — тоже.
- **`switchingTheDayBackAndForthNeverPaysAGiftOrAQuestTwice`** не менялся.

## 5. Отклонения, найденные проблемы, вопросы

1. **Найдена проблема: таймаут `player()` с этапа 2.2 на деле не срабатывал.**
   - Общий `Promise.await()` был построен на неотменяемом `suspendCoroutine`. `withTimeoutOrNull` вокруг такого ожидания не может его прервать: он ждёт завершения блока, то есть ответа промиса.
   - Поэтому зависший промис висел бы бесконечно, несмотря на таймаут. Это касалось 10-секундного таймаута `player()` в мосте, таймаута identity в `WebPlayerSessionController` (он упирается в тот же `player()`) и новых таймаутов облака.
   - Тесты этапа 2.2 этого не ловили: они подменяют мост фейками без JS-промисов.
   - Я перевёл `await()` на `suspendCancellableCoroutine`. Это нужно, чтобы таймауты пункта 2 вообще работали. Заодно заработали таймауты этапа 2.2.
   - Побочный эффект для остальных вызовов (платежи, лидерборды, загрузка ресурсов): если их корутину отменили, они перестают ждать сразу, а не после ответа промиса. Самый чувствительный случай — `purchase()`. Если его корутину отменят во время окна оплаты, подтверждённая покупка не обработается сразу, но её подберёт обязательная сверка `getPurchases()` при следующей привязке, так что двойного или потерянного начисления нет. В обычной игре эти корутины не отменяются: область страницы живёт всю сессию.
2. **Отклонение по коммитам.** Правка фразы о `WebClock` в `AGENTS.md` попала во второй коммит вместе с фразой о таймаутах, а не в коммит пункта 1. Так весь `AGENTS.md` правится одним коммитом.
3. **Вопрос по остаточным рискам часов** (раздел 2, пункт 1, риски 1–3). По-моему, своё монотонное время не нужно: SDK монотонный сам. Если площадка не передаёт `serverTime` в окружение, лучше узнать об этом из аналитики, чем строить вторую защиту.
