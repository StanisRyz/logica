## 2. Что сделано

### Пункт 1. Одно скорректированное время

- **`WebClock.kt`.**
  - `now()` возвращает `Date.now() + offset`.
  - `currentDate()` и `millisUntilNextLocalMidnight()` считаются от скорректированного времени в часовом поясе браузера. Используется один экземпляр `webClock`.
  - Смещение вычисляет `synchronize(serverTimeMs)`. Без серверного времени, или если оно не больше 0, смещение равно 0.
- **Источник серверного времени.** `ysdk.serverTime()` вызывается только в `YandexGamesBridge.serverTimeMs()`. Вызов обёрнут в JS-`try`, а NaN и не-числа дают `null`.
- **Когда синхронизируется.** `WebBootstrapController` вызывает `clock.synchronize(...)` в `onReady`, до перехода в `Ready`. Поэтому привязка Player и первый экран уже идут по скорректированному времени. В standalone синхронизации нет, смещение 0.
- **Кто перешёл на `WebClock`:**
  - восстановление жизней: `WebPlayerEconomyRepository` по умолчанию; таймер в `WebLivesRegenerationEffect`; `rememberNowMs`, то есть обратный отсчёт в магазине и в диалоге без жизней;
  - метка времени в истории покупок за гемы;
  - дата Daily и день наград: `BrowserLocalWebDailyDateProvider` (хаб, профиль, задания и подарок) и полуночный таймер (`millisUntilNextLocalMidnight`).
- **На `Date.now()` остались** кулдауны и грейс рекламы.
- **День наград только растёт.**
  - `claimLoginGift` выдаёт подарок только при `today > lastGiftEpochDay`.
  - `WebDailyRewardsSnapshot.on()` сбрасывает задания только при `today > epochDay`.
  - При `today < epochDay` (часы назад):
    - `claimQuest` возвращает `false`;
    - `plus` (учёт партии) ничего не меняет;
    - `claimedQuests(today)` отдаёт все задания как полученные, то есть недоступные;
    - в хабе подарок показывается полученным: `lastGiftEpochDay` передаётся как `min(last, today)`.
  - `mergedWith` не менялся.

### Пункт 2. Статистика

- **Ленивый компонент.** `loadLocal()` больше ничего не добавляет и не сохраняет. Компонент установки появляется при первом `recordTerminalResult`. Старые пустые компоненты остаются.
- **Размеры.**

  | Что | Размер |
  |---|---|
  | Бакет | 82 байта |
  | Заголовок компонента | 6 байт + id (у генерируемых id 32 символа) |
  | Типичный компонент (5 бакетов) | 448 байт |
  | Полный компонент (28 бакетов) | 2 334 байта |
  | Полный компонент с id максимальной длины (128) | 2 430 байт |

  В бюджет 40 КБ помещается около 90 типичных компонентов или около 17 полных. Прежний предел 120 КБ допускал до 50 компонентов (`MAX_DEVICE_COMPONENTS`, для чтения старых данных он сохранён).
- **Сжатие** (`WebStatisticsCompaction`, `MAX_ACTIVE_COMPONENTS = 12`).
  - Компоненты сверх 12 с наименьшим числом партий сворачиваются в `WebStatisticsArchive`: суммы счётчиков плюс множество свёрнутых id.
  - Компонент текущей установки не сворачивается никогда.
  - Множество id ограничено 8 КБ (`MAX_FOLDED_ID_BYTES`).
  - Худший случай: 12 полных компонентов с id по 128 символов, полный архив, бюджет id исчерпан — 39 666 байт. Это не больше 40 КБ, проверено тестом.
  - Сжатие выполняется при записи партии и после слияния.
- **Слияние.**
  - Свёрнутые id объединяются.
  - Компоненты с id из этого множества отбрасываются с обеих сторон.
  - Архивы сливаются по максимуму каждого счётчика.
  - Агрегат = компоненты + архив.
- **Формат.** Схема статистики 2 добавляет архив после компонентов. Снимок без архива по-прежнему пишется как схема 1, так что старые сборки его читают. Читаются обе схемы.
- **Бюджет конверта.**
  - `persist()` больше не бросает исключение: секция, которая не кодируется, или конверт больше бюджета дают `false`, а планировщик ставит `ERROR`. Раньше бросал `require`, и `false` получался только благодаря `runCatching` планировщика.
  - Сумма лимитов секций в целом бюджет не укладывается, подробности в п. 5.
- **Логика архива** целиком в `WebStatistics.kt` и `WebStatisticsRepository.kt`. `WebSaveManager` про него не знает.

## 5. Отклонения, найденные проблемы, вопросы

### Отклонения

- **Перенос id при сжатии.** В постановке задачи есть дыра. Устройство A может свернуть компонент установки X, которая ещё жива. Тогда при следующем слиянии X потеряла бы свой компонент, а все её новые партии каждый раз уходили бы в компонент, который снова отбрасывается. Поэтому X, увидев свой id среди свёрнутых, переходит на новый id установки (`WebInstallationIdProvider.rotate`). Партии X между сжатием на A и её следующим слиянием теряются: это допустимый недосчёт, а не пересчёт. Id установки общий для браузера, поэтому после смены у других Player в этом браузере старый компонент остаётся обычным, а новые партии идут под новый id. Без двойного счёта.
- **Ограничение множества свёрнутых id (8 КБ)** — это граница сжатия. Если бы при переполнении id выбрасывались из множества, старая копия вернула бы такой компонент и его партии посчитались бы дважды. Поэтому, когда бюджет id исчерпан, сжатие останавливается. Это около 60 установок с id максимальной длины или около 240 с обычными 32-символьными. Дальше компоненты растут, пока секция не упрётся в прежний предел декодера 120 КБ, после чего `persist()` честно не пишет. Гарантия «≤ 40 КБ» действует до этого порога.
- **«Повторить» при таймауте init** перезагружает страницу: повторить init внутри страницы мост не умеет, а SDK этого не поддерживает.
- **Строка `AGENTS.md` о Daily** вынесена отдельным коммитом `3eb7481`: в коммите пункта 4 я её забыл.

### Найдено, но не исправлено

- **Сумма лимитов секций.** Её нельзя уложить в бюджет конверта 100 000 байт без изменения форматов других секций, а это запрещено задачей. Лимиты по форматам:
  - статистика ≤ ~40 КБ — новые снимки этой сборки;
  - Daily ≤ 24 КБ;
  - магазин ≈ 4 КБ;
  - экономика, лучший счёт и награды — десятки байт;
  - прогресс каталога — до 10 000 записей;
  - звёзды — до 1 000 бакетов × 100 000 уровней;
  - журнал выдач — до 1 000 токенов по 384 байта.

  Реальные размеры на порядки меньше. При превышении `persist()` теперь возвращает `false` и статус `ERROR`, исключения нет.
- **Только `player()` получил таймаут.** Облачные `getData`/`setData` по-прежнему без таймаута. Зависание `getData` оставит восстановление или legacy-синхронизацию в ожидании, но игру это не блокирует.
- **Подмена часового пояса браузера** — принятый остаточный риск, как и сказано в задаче.

### Вопросы

1. Оставляем ли схему со сменой id установки, или лучше упростить сжатие? Простой вариант: компоненты сверх лимита отбрасываются без архива. Пересчёта нет, но суммы теряются.
2. Нужны ли таймауты на облачные `getData`/`setData`, по аналогии с `player()`?
